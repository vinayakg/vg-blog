F1
Email Acquisition Capture inbound emails and normalize into a standard internal format
EFFECT pollMailbox()
Connects to external email service on a scheduled interval. Fetches new messages since last checkpoint.
MailboxConfig → IO<RawEmail[]> Side effects: network I/O, reads external state
PURE deduplicateEmails()
Filters out already-processed messages by comparing message-IDs against the seen set. No external calls.
(RawEmail[], SeenSet) → RawEmail[] Pure: same input always → same output
TRANSFORM normalizeEmail()
Parses raw email into a structured canonical form: headers, body (plain + HTML), attachments as references, thread ID.
RawEmail → NormalizedEmail { id, threadId, from, to, cc, subject, bodyPlain, bodyHtml, attachmentRefs[], receivedAt, headers }
Mailbox (IMAP/Graph) → pollMailbox() → deduplicateEmails() → normalizeEmail() → NormalizedEmail impure shell → pure core
F2
Email Understanding Classify intent, extract entities, and assess sentiment — the "thinking" layer
GUARD redactPII()
Scans email content for PII (SSNs, account numbers, names). Replaces with tokens before LLM processing. Maintains a redaction map for later re-insertion.
NormalizedEmail → (RedactedEmail, RedactionMap) Pure: deterministic regex + NER rules
EFFECT inferIntent()
Sends redacted content to LLM for intent classification. Returns structured classification with confidence scores.
RedactedEmail → IO<Classification> { intent: Inquiry | Complaint | Request | Escalation | Informational, confidence: 0.0–1.0, reasoning: string }
EFFECT extractEntities()
LLM-powered extraction of domain entities: customer IDs, account numbers, product names, dates, monetary amounts.
RedactedEmail → IO<EntitySet> { customerId?, accountNumber?, products[], amounts[], dates[], references[] }
EFFECT assessSentiment()
Evaluates emotional tone and urgency. Outputs a sentiment score and urgency flag to guide downstream tone calibration.
RedactedEmail → IO<SentimentResult> { tone: Positive | Neutral | Negative | Angry, urgency: Low | Medium | High | Critical, emotionalMarkers: string[] }
PURE assembleUnderstanding()
Merges classification, entities, and sentiment into a single EmailUnderstanding record. No I/O — just combining the outputs from the three analysis functions into one structure.
(Classification, EntitySet, SentimentResult, NormalizedEmail) → EmailUnderstanding { email, intent, confidence, entities, sentiment, urgency } Pure: deterministic merge, no external calls
NormalizedEmail → redactPII() → inferIntent() + extractEntities() + assessSentiment() → assembleUnderstanding() → EmailUnderstanding parallel LLM calls, then pure merge
F3
Business Routing & Decision Apply business rules to decide what happens next — pure decision logic, no side effects
PURE evaluateRules()
Runs the email understanding against a rule table. Each rule maps (intent + entity patterns + sentiment) to a routing decision. Entirely deterministic — given the same rules and understanding, always returns the same route.
(EmailUnderstanding, RuleSet) → RoutingDecision { action: AutoReply | LookupAndReply | Escalate | Forward | Archive, templateId?, escalationTarget?, requiresDataLookup: boolean, priority: 1–5 }
PURE checkConfidence()
Evaluates whether classification confidence exceeds the threshold for automated processing. Low confidence routes to human review instead of agent pipeline.
(EmailUnderstanding, ConfidenceThreshold) → AutoProcess | HumanReview Pure: simple threshold comparison
PURE computePriority()
Calculates final processing priority from urgency, customer tier, SLA constraints, and email age. Used to order the processing queue.
(EmailUnderstanding, SLAConfig) → PriorityScore (1–100) Pure: deterministic scoring function
EmailUnderstanding → checkConfidence() → evaluateRules() → computePriority() → RoutingDecision entirely pure — no I/O, fully testable with unit tests
F4
Data Enrichment Fetch external data from core banking to build reply context — the impure shell
PURE buildLookupPlan()
Determines which external data is needed based on the routing decision and extracted entities. Produces a lookup plan — a list of queries to execute — without executing them.
(RoutingDecision, EntitySet) → LookupPlan [ { system: "CBS1", query: "getAccount", params }, { system: "CBS2", query: "getLoanStatus", params } ] Pure: plans the work, doesn't do it
EFFECT executeLookups()
Executes the lookup plan via MCP / Function Calling against core banking systems. Handles timeouts, retries, and partial failures. This is where side effects happen.
LookupPlan → IO<EnrichmentData> { accountDetails?, transactionHistory?, loanStatus?, productInfo?, lookupErrors[] } Side effects: network I/O to banking systems
TRANSFORM mergeContext()
Combines the email understanding with enrichment data into a complete ReplyContext. This is the full picture the drafting function needs.
(EmailUnderstanding, EnrichmentData, RoutingDecision) → ReplyContext { originalEmail, intent, entities, sentiment, customerData, routingAction, templateId, priority } Pure: structural merge only
RoutingDecision → buildLookupPlan() → executeLookups() → mergeContext() → ReplyContext pure plan → impure execute → pure merge
F5
Response Generation Draft, validate, and refine the reply email
PURE selectTemplate()
Chooses the appropriate response template based on intent classification and routing action. Returns template structure and tone guidelines.
(RoutingDecision, TemplateRegistry) → Template { structure, toneGuide, requiredSections, disclaimers } Pure: lookup from registry
EFFECT generateDraft()
Sends the full reply context and template to the LLM. Produces a structured draft email with greeting, body paragraphs, and closing.
(ReplyContext, Template) → IO<DraftEmail> { subject, greeting, bodyParagraphs[], closing, signature, disclaimers[] } Side effects: LLM inference call
PURE calibrateTone()
Adjusts the draft's language based on sentiment analysis. Angry customer → more empathetic phrasing. Routine inquiry → professional and concise. Applies deterministic rewrite rules.
(DraftEmail, SentimentResult) → DraftEmail Pure: rule-based tone adjustments
GUARD validateCompliance()
Checks draft against regulatory rules: required disclaimers present, no unauthorized promises, no disclosure of internal data, brand voice consistency.
DraftEmail → ValidationResult { passed: boolean, violations: ComplianceViolation[], suggestions: string[] } Pure: rule evaluation against draft
GUARD rehydratePII()
Re-inserts redacted PII back into the draft using the redaction map from F2. Customer names, account references are restored for the final email.
(DraftEmail, RedactionMap) → DraftEmail Pure: token replacement using map
TRANSFORM formatFinalEmail()
Assembles the complete email: applies HTML formatting, inserts signature block, attaches disclaimers, sets reply headers for proper threading.
DraftEmail → FinalEmail { to, cc, subject, htmlBody, plainBody, inReplyTo, references[], attachments[] }
ReplyContext → selectTemplate() → generateDraft() → calibrateTone() → validateCompliance() → rehydratePII() → formatFinalEmail() → FinalEmail
F6
Human Review & Approval Pause the pipeline for human judgment — the deliberate break in automation
EFFECT queueForReview()
Persists the final email and full context to a review queue. Notifies the assigned reviewer. Pipeline pauses here.
FinalEmail → IO<ReviewTicket> { ticketId, assignee, queuedAt, originalEmail, draftEmail, context } Side effects: write to queue, send notification
HUMAN reviewDecision()
Human reviewer examines the draft alongside the original email, classification reasoning, and enrichment data. Three possible outcomes: approve as-is, edit and approve, or reject with reason. This is not a function the system calls — it's a decision point where automation yields to human judgment.
ReviewTicket → HumanDecision { action: Approve | Edit | Reject, editedEmail?: FinalEmail, rejectionReason?: string, reviewerNotes?: string, reviewedAt: timestamp } Not a function — a human decision boundary
PURE applyReviewOutcome()
Routes the workflow based on human decision. Approve → proceed to dispatch. Edit → use edited version. Reject → return to classification or archive with reason.
HumanDecision → WorkflowNext { Approve → dispatch(finalEmail) Edit → dispatch(editedEmail) Reject → archive(reason) | reclassify() } Pure: pattern match on decision
FinalEmail → queueForReview() → reviewDecision() → applyReviewOutcome() → Dispatch | Archive | Loop automation pauses → human decides → automation resumes
F7
Dispatch & Record Send the approved email and record everything for compliance and learning
EFFECT sendEmail()
Delivers the approved email via SMTP / Graph API. Handles send failures, retries, and bounce detection.
FinalEmail → IO<SendResult> { messageId, sentAt, deliveryStatus: Sent | Bounced | Failed } Side effects: network I/O, sends email
EFFECT writeAuditRecord()
Persists the complete decision trail: original email, classification, enrichment data, draft, review decision, and send result. Immutable append-only log for compliance.
(NormalizedEmail, EmailUnderstanding, ReplyContext, FinalEmail, HumanDecision, SendResult) → IO<AuditRecord> Side effects: write to audit store
EFFECT emitMetrics()
Publishes processing metrics: end-to-end latency, per-function timing, classification accuracy (when feedback is available), and throughput counters.
(AuditRecord, Timestamps) → IO<void> Side effects: write to monitoring
Approved Email → sendEmail() → writeAuditRecord() → emitMetrics() → Done all side effects — the impure edge of the system

How This Differs from the Component Architecture

Component architecture answered: "What are the parts, where do they live, and how do they connect?" — it showed Docker containers, subnets, Kubernetes, and Azure services.

Functional architecture answers: "What does the system do, and how does data transform as it flows through?" — it shows functions, their inputs/outputs, their purity, and the pipeline of transformations from raw email to sent reply.

The key structural idea: Each function is explicitly tagged as pure (deterministic, testable with unit tests, no I/O) or effect (reaches outside the system boundary — LLM calls, database writes, network I/O). The architecture deliberately pushes decisions into pure functions (F3 is entirely pure) and isolates side effects at the boundaries (F1 ingestion, F4 banking lookups, F7 dispatch). This is the "functional core, imperative shell" pattern.

Why this matters: Every blue (pure) function can be tested with just inputs and expected outputs — no mocks, no test databases, no network stubs. The orange (effect) functions are where integration testing focuses. The pink (guard) functions are your compliance safety net. This separation makes the system dramatically easier to reason about, test, and audit.
